密度行列表示ブロック 実装仕様

密度行列表示ブロックのデザイン仕様から分離した実装仕様。 WebGPU 内部経路、外部 Qiskit Aer 経路、参照ファイル、受け入れ条件を扱う。 見た目、寸法、配色、ホバー、リサイズはデザイン仕様側を正とする。

§ 01 Qiskit / GPU 実装メモ (二系統経路)

密度行列表示ブロックは 2 つの計算経路を持つ: (a) WebGPU 内部実行 (qni 単体で動く既存経路、振幅 / 確率表示ブロックと同じ scheme) と (b) 外部 Qiskit Aer 経路 (qiskit-backend からの結果を受け取る経路、apps/qiskit-backend と統合)。 どちらも本番 UI 経路では GPU → CPU readback しない規約に従い、結果を GPU storage buffer に置いて render shader が直接 sample する。 span 8 は 216 = 65 536 セルの正方行列で、vec2<f32> として 512 KB を GPU storage で扱う上限になる。

(a) WebGPU 内部実行 (qni 単体、振幅表示ブロックと同パイプライン)

Quirk の densityDisplayStatTexture (DensityMatrixDisplay.js:44-71) を WebGPU compute pass 列へ移植:

  1. Control select + cycle — controls を満たす要素だけ詰めて span subspace を head に持ってくる (Quirk CircuitShaders.controlSelect + cycleAllBits)
  2. amplitudes → couplings — Quirk AMPLITUDES_TO_DENSITIES_SHADER と等価な compute kernel: ρij(rest) = ψi,rest · conj(ψj,rest) を各 rest 値ごとに計算し、出力 buffer に vec2<f32> で書き込む。要素数 = 2rest × 2span × 2span
  3. Partial trace (sum-fold) — rest 量子ビットについて sumFold で畳み込み、最終的に ρ: vec2<f32>[2span × 2span] の縮約密度行列が得られる
  4. unity 正規化 — unity = Σ ρii.real を reduce、ρ /= unity を全要素並列で適用 (Quirk densityPixelsToMatrix と等価)
  5. measured-bit decoherence — controls / lowering で得た is_measured_mask を渡して、(row ^ col) & mask != 0 な非対角を 0 に潰す compute pass (Quirk decohereMeasuredBitsInDensityMatrix と等価)
  6. render shader — 出力 storage バッファを fragment shader が直接 sample。outline / disk / needle / 外枠はすべて fragment shader 内の SDF で描く (振幅表示ブロックの amplitude_result シェーダと同型)

測定済みビットの decoherence

row / col の measured bit pattern が一致しない非対角を 0 化する。qni 側の lowering 順序は列処理の後に display captureなので、測定される直前の純粋振幅ではなく collapse 後の混合状態 が表示される。 

for row in 0..n:
  for col in 0..n:
    if ((row ^ col) & is_measured_mask) != 0:
      rho[row, col] = 0  // 位相 coherence が古典化で失われる

(b) 外部 Qiskit Aer 経路 (apps/qiskit-backend、実装済み)

外部 GPU 実行では、Web 側が配置済み Density Matrix 表示ブロックを outputs.densities に列挙し、qiskit-backend が QuantumCircuit.save_density_matrix(qubits, label=...) で縮約密度行列を保存する。応答は densities 配列で返り、各項目は gate_id / span / cells / unity を持つ。cells は行優先の [re, im] 配列で、サイズは 2span × 2span 複素数。

  • バックエンド側 — contract.py が outputs.densities を検証し、span 1〜8 / 最大 16 件 / 保存対象 span と非表示 control bit の合計 8 以下を受け付ける。runners.py は各列のゲート適用直後に save_density_matrix を挿入し、control_mask / control_value に合う densities[].cells へ変換する
  • Web 側要求 — apps/web/src/app/external_gpu/density.rs が {"gate_id", "column", "span", "base_bit", "control_mask", "control_value"} を生成する。Control と同じ列に置いた Density Matrix 表示ブロックも、内部 WebGPU 実行と同じ条件付き表示として外部 GPU 経路へ送信する
  • Web 側描画 — 応答 JSON を Float32Array 相当の連続値へ平坦化し、DensityMatrixDisplayCallback が density_output / density_meta GPU バッファへ queue.write_buffer で転送する。転送後の描画は (a) と同じ DENSITY_RENDER_SHADER が担当する
  • 測定済み wire の注意 — 現在の外部経路は Aer の保存結果をそのまま表示する。測定済み wire の非対角を WebGPU 内部実行と完全一致させるための追加 decoherence pass は今後の改善候補

★ 批評 · § 01 Qiskit / GPU 実装メモ
経路 (a) / (b) のスイッチ UI 仕様が無く、ユーザが「どっちで動いているか」を知る術がない

経路 (a) WebGPU 内部と (b) 外部 Qiskit Aer は推奨用途 (span ≤ 6 リアルタイム vs span 7〜8 精密検証) が異なるが、 ユーザが UI でどちらを選ぶかの仕様が本セクションに無い。 「スイッチは ExecMode 設定と一致させる」と書かれているが、ExecMode の UI 表現や、密度行列表示ブロック側の「今 a / b どっちで描画しているか」を伝える視覚指標が定義されていない。 改善案: widget の右下に小さな (a) / (b) badge を表示する (例: 文字 "L" = Local WebGPU / "Q" = Qiskit、Flexoki tx-3 で控えめに)。 ユーザが span 6 を超えて (b) の方が安定だと知ったとき、UI から経路を切り替える導線が必要。

経路 (b) の decoherence 未実装が「今後の改善候補」のまま放置

本文に「測定済み wire の注意 — 現在の外部経路は Aer の保存結果をそのまま表示する。測定済み wire の非対角を WebGPU 内部実行と完全一致させるための追加 decoherence pass は今後の改善候補」と書かれているが、 これは経路 (a) と (b) で同じ回路に対して異なる行列が表示されることを意味する。 ユーザは「同じ Bell state なのに、Local モードと Qiskit モードで非対角の値が違う」という再現性の破れに遭遇する可能性がある。 改善案: (1) 経路 (b) でも qni 側で post-process decoherence を適用する compute pass を追加する、または (2) 本仕様に「measured wire を含む場合は経路 (a) のみサポート」と明示制約を入れて経路 (b) で reject する。 現状の「今後の改善候補」は決定保留であり、ユーザに混乱が生じる前に方針を固める価値がある。

レイテンシ「backend RTT 依存 (典型 100 ms〜数秒)」の UX 影響が定量化されていない

§ 01 表に「(b) レイテンシ: backend RTT 依存 (典型 100 ms〜数秒)」とあるが、density 表示ブロックが drag / resize 中にこのレイテンシで動くと「ハンドル動かしてから数秒後に描画が更新される」という体験になる。 振幅 / 確率表示ブロックの (a) WebGPU 経路は frame 内 (16 ms 程度) で完結するので、表示ブロック族全体の体感速度が経路選択で激変する。 改善案: drag / resize 中は強制的に経路 (a) (= placeholder + 暫定描画) を使い、操作完了後に (b) で精密な値を取り直す、というhybrid モードを仕様化する。

§ 02 実行前プレースホルダ描画

GPU 経路の density_output / density_meta バッファがまだ書き込まれていない段階では、既存 GPU 描画パイプラインの DensityInstance.render_mode に 「sample / placeholder」 フラグを持たせ、fragment shader 側で描画を分岐する。 placeholder なら purple-100 背景 + 外枠だけを描き、それ以外は通常の probability + disk + needle を描く。

  • CPU から空の行列値を計算しない
  • placeholder 専用の render pass は追加しない
  • 全 span で背景の薄紫一色 + 外枠だけを描く
  • 見た目の仕様は デザイン仕様 § 07 を正とする

★ 批評 · § 04 受け入れ条件
「経路 (a) と (b) が同じ回路で同じ結果を返す」整合性テストが定義されていない

受け入れ条件は経路 (a) の known-state assert (項目 4) と経路 (b) の Aer API 確認 (項目 6) を独立に並べているが、 「同じ回路を (a) と (b) で実行して結果が一致する」整合性テストが無い。 § 01 で「経路 (b) の measured wire decoherence は今後の改善候補」と認めている以上、現時点でも (a) と (b) で異なる行列が返ることが既知の状態。 これをテストで明示的に「measured wire を含まない回路では (a) と (b) が一致する」「measured wire を含む回路では (a) のみ採用」と仕様化しないと、回帰検出のフックが弱い。

改善案: 受け入れ条件に「(a) (b) 整合性」項目を追加し、(1) Bell state, span 2 (measured wire なし) → (a) と (b) の cells 配列がいずれの成分も |Δ| < 1e-3、(2) measured Bell state → (a) のみ採用 (= (b) は reject) を assert する。 テスト粒度として「1 ケース 1 assertion」を守りつつ、(a)(b) 整合性は独立した観点なので別 case として分離する。

visual snapshot が span 1 / 4 / 6 / 8 の 4 枚で「対角と非対角」「pure と mixed」の網羅が不足

項目 7 の visual snapshot は cellPx 帯別 (full / outline+disk / heatmap) の代表 4 枚を撮るが、 本表示ブロックの固有の論点である「対角 vs 非対角の disk スケール」「pure vs mixed の判別」「Bell の対角四隅パターン」が snapshot として明示されていない。 改善案: span 2 の Bell (純粋) / span 2 の I/4 (最大混合) / span 4 の 50% 混合 / span 6 の random circuit state の 4 枚を「state 種別による snapshot」として追加する。これで cellPx と state の 2 軸の回帰検出が機能する。
