● Internal · project orientation · 2026

qni-webgpu — a Rust + WebGPU rewrite of qni.

Quantum-circuit playground in the browser, but with every state-vector gate dispatched on the GPU and every pixel drawn from a single <canvas>. No React, no DOM trees of qubits — just Rust compiled to WebAssembly talking to wgpu.

Lang. Rust 2021 · TypeScript Render. WebGPU via wgpu 27 UI. egui / eframe Bundle. wasm32-unknown-unknown via Trunk Cap. ≤ 16 qubits (state-vector)
01

1 言語 / 1 canvas / 1 wasm

HTML/CSS で UI を組み立てる代わりに、Rust の egui アプリを丸ごと <canvas> に描く。フォーカス管理も DOM も Custom Elements も使わない。

02

状態ベクトルは GPU 完結

ゲート適用・ブロッホ球縮約・測定崩壊・popup の数値表示まで WGSL の compute / fragment で完結。production 経路で map_async readback はしない。

03

"qni のリプレース" ではない

本家 qni (Rails + Web Components) は仕様の参照元。シミュレーションロジック・UI 規約・配色・ゲート種は qni と互換、内部の作り方は完全に別物。

§ 01 Stack at a glance

各レイヤで使っている技術を、「これは何」と「このプロジェクトでどう使うか」の 2 段で説明する。バージョンは 2026-05 時点の Cargo.toml / package.json 由来。

Language
Rust 2021 (stable)
TypeScript 5.x

Rust — C/C++ 系のシステム言語。ガーベジコレクタを持たない ので実行時オーバーヘッドが小さく、所有権 (ownership) と借用 (borrowing) の型システムでメモリ安全をコンパイル時に 保証する。`cargo` でビルド・テスト・依存解決まで一括。ネイティブ実行ファイルにも WebAssembly にも同じソースからコンパイルできるのが本プロジェクトの肝。

UI / シミュレーション / GPU パイプライン本体はすべて Rust。TypeScript はブラウザ起動時の wasm 読み込み glue (bootstrap.ts) と Playwright / Cucumber のテスト補助に限定。

UI
egui 0.33
eframe 0.33

egui — Rust 製の GUI ライブラリ。"immediate-mode" 方式を採る。React や DOM が "retained-mode" (ウィジェットの木を一度作って保持し、変更があるところだけ更新) なのに対し、immediate-mode は 毎フレーム UI 全体を関数として再宣言する。`if hovered { show_tooltip() }` のような素直なコードがそのまま動く。状態は単一の構造体 (`QniApp`) に集約されるので、virtual DOM ↔ real DOM のような二重表現の同期問題が無い。

eframe — egui を OS / ブラウザの window に接続するランナー。アプリのライフサイクル (init / update / repaint) を管理し、入力イベントを egui へ渡す。本プロジェクトでは web backend を使い、ブラウザの <canvas> 1 枚に egui を描かせている。

GPU
wgpu 27 (WebGPU backend)

WebGPU — WebGL の後継となる、ブラウザから GPU を直接叩くための新しい標準。WebGL に無かった compute shader (汎用 GPU 計算) が使えるのが最大の差。Chrome / Edge では既定で有効、他ブラウザは flag 有効化が必要な段階。

wgpu — Rust 製の WebGPU 仕様実装。ブラウザでは WebGPU、ネイティブでは Vulkan / Metal / D3D12 / OpenGL のいずれかに自動 fallback する クロスプラットフォーム GPU 抽象 を提供する。同じ shader / pipeline 定義が `apps/web` (wasm) でも将来の native ビルドでも動く。本プロジェクトでは依存量を削るため features = ["webgpu"] だけを有効化し、他 backend は切り落としている。

Shader
WGSL — 5 module
state / bloch / measure / digit / popup_value

WGSL (WebGPU Shading Language) — WebGPU 用の shader 言語。GLSL や HLSL に相当するが、よりモダンで型に厳しい。GPU 上で動く小さなプログラムを書く。種類は (a) compute shader (汎用並列計算)、(b) vertex / fragment shader (描画) の 2 系統。

このプロジェクトの shader は gpu/shaders/*.wgsl に置かれ、include_str! で &'static str として埋め込まれており、起動時に wgpu がコンパイルする。compute 側はゲートの状態ベクトル適用 / ブロッホ球縮約 / 測定崩壊を、fragment 側は状態ベクトル円・ブロッホ矢印・測定 0/1・popup 数値の描画を担当する。

Bundle
wasm32-unknown-unknown
Trunk · wasm-bindgen

WebAssembly (wasm) — ブラウザで動くバイナリ形式の実行コード。JS と並んで browser native。Rust や C++ をコンパイル先に指定すると、ネイティブと同等の速度で動く小さな実行可能ファイル (.wasm) を吐ける。wasm32-unknown-unknown は「32-bit wasm / OS なし / 標準ライブラリの I/O は browser API 経由」というターゲット三組。

Trunk — Rust → wasm 用のビルドツール。`cargo build` を実行 → wasm-bindgen で JS↔Rust 呼び出し glue を生成 → 静的アセットを `dist/` にコピー → 開発サーバとして配信、までを 1 コマンドで行う。HTML <link data-trunk> 経由でアセットを宣言的に組み立てるのが特徴。

wasm-bindgen — Rust 関数を JS 側から呼べる形に変換するブリッジ生成器。本プロジェクトでは Window / Document などの browser API 呼び出しと、テストハーネスの window.__eguiReadStateVector() に使っている。

Style
Flexoki Light palette
Tailwind 既定スケール

Flexoki — Steph Ango (kepano) が設計した、紙とインクの質感をモチーフにした小さな色トークン集 (github.com/kepano/flexoki)。`paper` / `bg-2` / `ui-2` / `tx-2` / `blue-600` のような名前で意味の付いたトーンで、明色・暗色の 2 系統を持つ。本プロジェクトは Light だけを厳密に使い、独自の `sky-500` などは禁じている。

Tailwind 既定スケール — CSS フレームワークの方ではなく サイズの目盛りだけ を借りる。フォントサイズは `text-xs` (12px) / `text-sm` (14) / `text-base` (16) / `text-lg` (18) などの段階だけ、spacing は 4px 倍数 (`spacing-1` = 4 / `spacing-2` = 8 / …) のみ使う。13px / `px-3.5` のようなスケール外の値は書かない。

Test
Playwright + Chromium
Node test runner

Playwright — Microsoft 製のブラウザ自動操作フレームワーク (Cypress や Selenium と同じ系統)。Node.js から Chromium / Firefox / WebKit を起動して、クリック / ドラッグ / スクリーンショット撮影 / コンソール検査 ができる。本プロジェクトでは 実 WebGPU を有効化した Chromium を使うので、shader / wasm の挙動を実機相当で検証できる。

spec は apps/web/tests/web-*.spec.ts に機能別 (drag / error / gpu / interaction / palette / state-semantics) に分かれている。GPU 上の状態ベクトルを取り出すために、wasm から `window.__eguiReadStateVector()` という on-demand readback API だけ公開している。これが production-readback ルールの唯一の例外。

CI
GitHub Actions

毎 push で以下が走る: cargo fmt --check (整形差分ゼロ) / cargo clippy -- -D warnings (lint 警告も全部エラー扱い) / cargo build --release --target wasm32-unknown-unknown (wasm リリースビルド) / pnpm exec playwright test (実 Chromium / WebGPU)。

UI のスナップショットは cargo insta で管理しており、CI で cargo insta pending-snapshots も走らせる。誰かが review し忘れた `.pending-snap` がリポに残っていれば fail する仕組み。

Adjacent app
apps/tui (ratatui)

apps/tui — 同じ回路モデルを ターミナルで 描くプロトタイプ。ratatui + crossterm で動き、wasm を立てなくても素早く動作確認ができる。配色も Flexoki トーンの ANSI 近似で揃えている。

§ 02 Two-lane architecture

毎フレームの仕事を、CPU 側 (Rust / wasm) と GPU 側 (WGSL pipelines) の 2 レーンに完全に分けている。CPU 側は「何を計算したいか」を組み立て、GPU 側が「実際に数値を作って描く」。

CPU lane · src/app · src/render

app/ QniApp::update
回路状態 + drag / hover / scroll の保持。update_flow, drag_controller, state_panel 等の submodule に責務分割済み。
simulation_plan/ linearize
placed_gates → Vec<SimulationOp> (Apply / CaptureBloch / MeasureReduceSample / MeasureCollapse) を線形化。CZ / Phase-pair / Swap の意味付けはここ。
render/ circuit_* · state_panel_*
回路 / palette / 接続線 / popup を egui Painter に発行。GPU 描画する箇所だけ egui_wgpu::Callback として GPU レーンに橋渡し。
url_circuit/
qni 互換 JSON ↔ Vec<PlacedGate>。#{"cols":[…]} hash でリンク共有。
eframe · egui_wgpu callbacks · storage / uniform buffers

GPU lane · src/gpu

gpu/resources/ common · state · bloch · measure · probability · digit · popup_value
subsystem 毎に pipeline + bind group + params バッファをオーナーシップ。state buffers は ping-pong で gate ごとに in/out 反転。
gpu/recompute.rs
SimulationOp を 1 つの command encoder に展開。Apply は state_count/2 並列、CaptureBloch / MeasureReduce は workgroup 1 で in-place 縮約。
gpu/shaders/ state · bloch · measure · probability · digit · popup_value
WGSL ソース。compute = ゲート適用 / Bloch / 測定。render = 状態円 / ブロッホ矢印 / 測定 0/1 / popup 数値、すべて storage バッファを直接 sample する。
gpu/readback.rs · test only
JS から window.__eguiReadStateVector() 等を呼ばれたときだけ map_async。production 経路は通らない。

線形化された sim_ops がレーンの唯一の API。CPU 側は完了した circuit description を渡し、GPU 側は state バッファを更新してそのまま render に流す。間に CPU を経由する数値は本番では一切ない。

§ 05 Performance principles

「とりあえず動く」と「ドラッグしてもガタつかない」は別物。docs/web-perf-audit.html の Issue A〜G が原則の出どころで、A〜C は既に潰してある。

resolved
— principle A

1 recompute = 1 submit

毎ゲートで queue.submit していた頃は CPU↔GPU の wakeups が支配項だった。今は recompute.rs が 1 encoder にすべての compute pass を積んで 1 回だけ submit する。staging buffer に params を一括書き込みし、各 dispatch 直前に copy_buffer_to_buffer で uniform スロットへ差し替える。

gpu/recompute.rs

resolved
— principle B

params dirty flag

render / overlay / digit / popup の各 params buffer は subsystem ごとに last_*_params: Option<…> を持ち、フレーム前後で変化が無ければ queue.write_buffer をまるごと省く。viewport や色がそのままなら毎フレームのアップロード 3 本がゼロになる。

gpu/resources/{state,bloch,digit,popup_value}.rs

resolved
— principle C

|0…0⟩ 初期化も GPU で

recompute 開始時に encoder.clear_buffer(state_buffers[0]) → copy_buffer_to_buffer(seed → slot 0)。(1.0, 0.0) の 8-byte seed を持っておき、CPU で 65,536 振幅の Vec を確保していた頃のメモリピークを 0 に。

gpu/resources/common.rs · gpu/recompute.rs

— principle D

state buffer ping-pong

state vector 用ストレージは 2 本。ゲートごとに in / out を入れ替える。compute_bind_groups[0/1] と measure_collapse_bind_groups[0/1] の 2 セットを事前に作っておくので、bind group の再構築は無い。

gpu/resources/common.rs

— principle E

render shader が storage バッファを直接 sample

state 円 / ブロッホ矢印 / 測定 0/1 / popup 数値はすべて 同じ GPU 上の値を fragment shader から直接読む。CPU 経由しないので 1 frame 遅れも staging 割り当ても発生しない。値の表示が常に最新フレームの計算結果と同一であることが保証される。

gpu/shaders/{state_render,bloch_overlay,measurement_digit,popup_value}.wgsl

— principle F

drag 中は描画を簡略化

tessellator 負荷を下げるため、ドラッグ中は角丸・影・アイコン線・接続線を抜いてテキスト描画に切り替える。state vector の再計算は drop / snap の瞬間だけに絞り、CPU は repaint pacing にだけ集中する。

app/drag_controller/preview.rs · render/circuit_gates.rs

— principle G

repaint throttle (CooldownThrottle 風)

Quirk の REDRAW_COOLDOWN_MILLIS=10 を踏襲。ドラッグ中は 10 ms base + 0.1× ポンプで request_repaint / request_repaint_after を切り替え、フレーム間隔を間引きする。

app/update_flow.rs · constants.rs

— principle H

16 量子ビット cap (1 dispatch で並列)

state-vector アプローチで現実的に動く上限を 16 量子ビット (= 2¹⁶ = 65,536 振幅) に絞る。それ以上は将来 qiskit + GPU backend にまわす設計判断。1 ゲート = state_count / 2 並列を 1 dispatch で消化できる。

constants.rs · MAX_STATE_COUNT

§ 06 GPU-side text rendering

状態ベクトルセルの hover popup には「振幅 / 確率 / 位相」の 数値 が表示される。これらの数値は GPU のメモリ上にある state vector から計算するもので、CPU に戻して文字レイアウトしては 「本番で GPU → CPU readback しない」ルールに違反 する。
解決策: 文字も丸ごと fragment shader (GPU で動く、ピクセル 1 個ずつ色を決める小さなプログラム) で描く。仕組みは "baked glyph atlas + per-pixel digit extraction" の 2 段だが、まずは用語から。

— このセクションだけで使う用語
glyph
「1 文字分の絵柄」。文字コード上は同じ "A" でも、フォントごとに描かれる形 (= glyph) は別物。ここでは 0..9 . + − i % ° の 16 個の glyph を扱う。
atlas
「たくさんの小さな絵を 1 枚にまとめたテクスチャ」。ゲーム開発では「sprite atlas」と呼ばれる、まったく同じ概念。1 枚のテクスチャに 16 個の glyph を横並びで詰めて GPU にアップロードする。
bake / rasterize
「ベクター形式の文字を、ピクセルの白黒画像に焼き付ける」操作。フォントファイル (TTF) は曲線で文字を表していて、そのままでは GPU で sample できない。起動時に 1 回だけピクセル化して atlas に置く。
R8Unorm
テクスチャの「1 ピクセル = 8 bit × 1 チャンネル」フォーマット。色を持たず、0〜255 の濃淡だけ。今回は「インクの濃さ」として使うので RGB は要らない。
UV
テクスチャ内を 0..1 で示す座標。(u, v) = (0.5, 0.0) なら「テクスチャの上端の真ん中」。シェーダはこの UV を使って atlas からピクセルを取り出す。
textureSample
WGSL の組み込み関数。textureSample(tex, sampler, uv) でテクスチャから 1 ピクセルの色を取り出す。これが「atlas からこの glyph のこのピクセル」を取ってくる本体。

idle
